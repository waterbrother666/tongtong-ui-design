# 项目化视觉选项与提问

当用户提供目标项目，希望基于后端功能设计页面，或从零设计页面，但尚未确定视觉方向或关键组件时使用。本文件规定的是**给用户选择的方式**；库间能力仍由 `selection-matrix.md` 判断。不要把所有库罗列成一份问卷。

## 先识别不可选与可选部分

1. 阅读项目已有路由、页面、设计 token、UI 原语和后端契约。确认字段、操作、权限、加载/空/错误/成功状态，以及移动端需求。可从仓库判断的事实不再问用户。
2. 功能语义不可为了风格而变化。比如后端需要可分页、可筛选的订单列表，就先确认表格能力；用户选择的是信息密度、视觉层次和合适的组件实现，不是是否保留分页或错误恢复。
3. 只挑会影响结果的决策提问：整体视觉方向，以及表格、导航、表单、审批、图表、AI 状态或动效中的关键一两项。普通 Button、Input 不逐个问。
4. 候选项必须与当前框架、依赖和交互原语兼容。不能为了凑满选项展示明显不合适的视觉特效；通常给出 2–3 个真正可行的方向，允许“由你推荐”。

## 候选组件必须有可核对的网址

- 每个候选项都写清楚组件库、**具体组件名**，并链接到其官方组件演示页或文档页；优先可直接看到交互的页面，不只给组件库首页。
- 一个风格方案若组合多个关键组件，分别给出每个关键组件的直达链接和职责；不要用一个组件库首页代替整组链接。对于 GSAP 等提供的是动画能力而非现成 UI 组件的来源，标为“能力参考”，链接官方对应功能文档或演示，不伪称可直接安装的组件。
- 链接在提问前实时核对。若上游只有源码页，就标为“官方源码”，不要称作在线演示；找不到有效直达链接的组件不能作为可点击预览选项。
- 区分“可获取的组件”和“设计灵感”。图库、第三方产品页面只能启发构图或风格，不能声称有安装命令或复制许可。
- 说明获取方式：已有项目组件、registry、CLI、Package、Skill/MCP 辅助发现，或需原创实现。Skill/MCP 本身不是运行时组件。
- 用户选择后，只有上游许可允许且项目兼容时才按官方方式安装/复制源码；否则借鉴视觉原则，写原创实现，不复制第三方产品页面代码。

## 生成让人一眼能比较的 Markdown

优先使用目标项目已有的设计文档目录；没有约定时写入 `docs/ui-proposals/<page-slug>.md`。不要覆盖现有文件。先生成文件并检查显示效果，再在聊天里给用户可点击路径。若用户禁止写文件，则在回复中直接展示同样的 Markdown 草图，并明确说明没有保存文件。

文件至少包括：

1. 页面/功能目标和从项目核对到的约束；明确这是“候选方案”，不是已实现界面。
2. 每个选项的视觉草图。用同一内容、同一视口比例和近似尺度比较形状、间距、密度与布局。**草图必须画出来**，不能用形容词代替。
3. 风格或关键组件的候选编号、推荐项、组件级优势、官方直达链接、引入依赖/兼容限制。
4. 对后端功能的映射：每个区域显示什么字段/操作，以及加载、空、错误、成功和权限状态如何呈现。
5. 一句可直接回答的选择题，例如“整体选 A 还是 B？表格选 1 还是 2？也可以回复由你推荐”。

每个方案按同一顺序组织：“视觉草图 → 关键区域和组件直达链接 → 组件级优势与代价 → 与后端字段/操作/状态的映射”。这样用户看到形状后，可以直接点开对应组件核对实际效果，再做选择；文件和聊天中的方案编号须一致。

低保真阶段可用等宽 `text` 代码块直接画线框。下面是**同一张信息卡**的形状对比示例；实际输出应替换为用户项目的内容和组件：

方案 A：圆润、舒展

```text
      ◯  头像
╭──────────────────────────╮
│  标题                    │
│  ╭────────╮  ╭────────╮  │
│  │ 主要操作│  │ 次要操作│  │
│  ╰────────╯  ╰────────╯  │
╰──────────────────────────╯
```

方案 B：方正、紧凑

```text
┌──────────────────────────┐
│ □ 头像  标题              │
├──────────┬───────────────┤
│ 主要操作 │ 次要操作      │
└──────────┴───────────────┘
```

如果颜色、精确圆角、阴影或复杂形状决定了选择，应在同目录生成原创 SVG，并用 Markdown 图片语法按相对路径嵌入；同时保留一张简短字符线框作无法显示 SVG 时的降级。SVG 是示意而非上游组件截图，不能把示意图误称为真实组件预览。验证目标 Markdown 阅读器中图片能显示、相对路径有效，窄窗口也能比较。动画用静态关键帧或线框解释，再链接官方实时演示。

## 提问与实施边界

- 聊天消息只摘要差异和推荐理由，附 Markdown 文件链接及重点组件的官方直达链接；细节放在文件中。不要要求用户先读完长篇库文档才能回答。
- 先问整体风格，再问必要的关键组件；如某组件完全由功能/兼容性决定，就直接说明推荐，不制造虚假的选择。
- 用户选择后，在方案文件中记录最终选项和理由，再按授权实施、运行与浏览器验证。若用户只要选型或视觉方案，到此为止。
- 用户给出明确视觉参考、指定组件或说“你决定，直接做”时，跳过多余问卷；仍核对组件来源并在交付中说明实际选择。
