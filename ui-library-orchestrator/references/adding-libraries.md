# 收录新的 UI 来源

只有在核对官方文档或代码仓库后才能收录新来源。在 `references/libraries/` 中为它创建一个聚焦文件，并同步更新 `selection-matrix.md` 和 `SKILL.md` 中的路由列表。

## 必须记录的内容

- 官方文档和代码仓库 URL。
- 核对日期，以及可获取时的仓库提交或发布版本。
- 交付方式：Package、复制式 Registry、CLI、Skill、MCP、Template 或多种方式的组合。
- 支持的框架和已验证的版本前置要求。
- 用产品语言说明它最擅长的场景。
- 按组件级能力分组，使用真实、当前有效的组件名。
- 从官方来源核对过的安装或访问流程。
- 样式模型，以及如何在不破坏原生行为的情况下适配目标项目。
- 会影响选型的可访问性、性能、许可证、Beta、收费或平台约束。
- 哪些情况应该让现有其他库胜出。
- 该来源独有的浏览器和功能检查。

## 更新选型规则

每收录一个新来源，都要在矩阵中回答：

1. 它能明显更好地处理哪个现有场景？
2. 具体是哪个组件带来该优势？
3. 选它之前需要从目标项目获得什么证据？
4. 它与现有来源的重叠区域是什么？
5. 平局时如何决定？

不要只因为某个库有一批好看的组件就把它加入目录。如果无法说清它的优势和选型边界，就先保持为“未分类候选”，直到真实任务证明其价值。

## 获取方式规则

- Skill 提供流程知识，不证明运行时兼容。
- MCP 提供发现或获取能力，不能取代源码审查、差异检查和浏览器验证。
- CLI 会修改目标项目；必须在正确项目根目录运行，并检查它修改的全部内容。
- Package 会引入依赖边界；要验证 peer version、bundle/运行时影响和样式集成。
- 复制式 Registry 允许定制源码；但要保留上游行为，并记录有意做出的本地改动。
